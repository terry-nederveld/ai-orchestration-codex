# Context

Long-running work outlives model sessions and local processes. Coding output is authoritative in Git, while discovery and requirements output must remain understandable in the originating work system.

# Decision

Create immutable, revisioned `ExecutionSpecification` records. A revision contains goals, acceptance/completion criteria, normalized work relationships, repository roles, effective instructions and provenance, promoted context, workflow outputs, dependencies, tests, tools, permissions, validation, profile, and authoritative-source fingerprints.

Coding checkpoints record remote branch and commit SHA and push before long suspension. Non-code checkpoints update a delimited managed section while byte-for-byte preserving content outside it. Resume reconciles authoritative changes and creates revision N+1 only when the effective specification changes.

# Rationale

This makes replacement sessions deterministic without pretending conversation transcripts are durable work products.

# Alternatives Considered

- Save complete prompts only: rejected because prompts lose provenance and merge semantics.
- Store all state in issue comments: rejected because comments become noisy and hard to reconcile.
- Store implementation patches only in the database: rejected because Git already provides collaboration, identity, and recovery.

# Consequences

Checkpoint policies must handle branch collisions and push failures. Managed-section updates require conflict-safe provider writes.

# Implementation Notes

Instruction and context inputs are treated as untrusted evidence, retain provenance, and are never promoted silently.
