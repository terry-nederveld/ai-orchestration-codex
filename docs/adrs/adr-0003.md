# Context

The system has many legitimate variation points but initially runs on one machine. It must support local, service, and future remote deployments without premature distributed-system complexity.

# Decision

Build a modular hexagonal monolith. Pure domain types and state machines sit at the center. Application services depend on ports. Provider, persistence, workspace, tool, and transport adapters implement those ports. A composition root is the only place that selects concrete implementations.

# Rationale

This yields independently testable components and provider-neutral domain logic while retaining simple transactions, deployment, debugging, and refactoring. A future remote worker boundary can be introduced at application ports without rewriting the domain.

# Alternatives Considered

- Microservices add network failure, deployment, and consistency cost before the product needs independent scaling.
- A plugin-first collection of scripts would be quick initially but would not provide stable orchestration semantics or durable state.
- A single service class would reduce files but couple vendors, workflow policy, execution, and persistence.

# Consequences

Module boundaries require architectural tests and disciplined imports. In-process calls remain efficient. Later distribution requires transport adapters around existing ports.

# Implementation Notes

Organize source by domain, application, ports, and adapters. Domain code cannot import infrastructure or UI modules. Registries provide runtime composition without vendor conditionals in the kernel.
