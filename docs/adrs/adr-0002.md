# Context

The product needs native installers for macOS, Windows, and Linux, local filesystem and process access, secure secret storage, notifications, auto-update support, and a responsive UI. The TypeScript orchestration service must also run headlessly.

# Decision

Use Tauri 2 for the desktop shell and package the same Node control-plane executable used by the CLI as a target-specific sidecar. The renderer communicates with the local service through a narrow loopback API. Tauri owns application lifecycle, capabilities, secure desktop storage, notifications, and updates.

# Rationale

Tauri uses the operating system webview, provides explicit capability controls, supports target installers and sidecars, and avoids embedding a second Chromium distribution. A sidecar preserves one orchestration implementation across desktop and headless modes.

# Alternatives Considered

- Electron offers the simplest Node integration, but ships Chromium, increases resource and update burden, and gives the privileged main process a larger attack surface.
- A fully Rust Tauri backend would avoid a sidecar but duplicate or rewrite the provider and runtime layer selected in ADR 0001.
- A browser-only UI cannot safely provide the required local process, filesystem, and credential functionality.

# Consequences

Desktop packages remain relatively small and the renderer stays unprivileged. Packaging requires one sidecar binary per target triple and a supervised startup handshake. The loopback API needs an ephemeral bearer token and must never listen on a non-loopback interface by default.

# Implementation Notes

Use Tauri capabilities with the minimum commands. Compile the sidecar during packaging, pass its authentication token outside command-line arguments where possible, terminate it with the application, and keep the renderer sandboxed from secrets.
