# Context

Fable v0.1 compiles a dependency graph from YAML and persists step snapshots, but a running record identifies a workflow only by mutable ID. Engine lifecycle, graph position, domain state, and external tracker state can consequently be confused during recovery or projection.

# Decision

Every published workflow and policy asset is immutable and addressed by logical ID, positive version, and canonical SHA-256 digest. Starting a run pins a resolved snapshot containing the root workflow plus referenced sub-workflows, profiles, gates, rubrics, and policies. Editing publishes a new version for future runs.

Run state is separated into reserved engine lifecycle, workflow graph position, unrestricted domain state, and external state projections. Only the engine advances the declared graph. Agents produce structured data but cannot mutate the graph.

# Rationale

Recovery and audit require the exact executable policy, not whatever currently has the same name. Separate state layers prevent a tracker status or customer-defined state from accidentally acquiring engine semantics.

# Alternatives Considered

- Reload the latest YAML on resume: rejected because it changes in-flight behavior.
- Store only a Git revision: rejected because workflows may combine local and remotely supplied assets.
- Model workflows as a finite-state machine only: rejected because parallel graphs, joins, waits, and sub-workflows are first-class.

# Consequences

Published versions consume additional storage and require explicit lifecycle management. Runs remain reproducible and can explain every pinned input.

# Implementation Notes

Canonicalization sorts object keys recursively. Version publication is idempotent for an identical digest and rejects conflicting content for an existing version.
