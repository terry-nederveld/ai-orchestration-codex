# Context

Fable must continuously turn eligible external work into runs without dispatching the same item repeatedly. Provider webhooks are not uniformly available, especially for local and self-hosted installations. Process interruption must leave explicit, inspectable state.

# Decision

Run a polling scheduler inside the local control-plane process. Configure sources declaratively, bound global concurrency, persist one deterministic dispatch record per source and work item, and apply bounded exponential retry. On service restart, mark interrupted runs failed, expire orphaned approvals, and move interrupted dispatches to retry or exhaustion.

# Rationale

Polling is consistent across GitHub, Jira Cloud, Jira Data Center, and Linear and keeps the first release deployable on one machine. Durable dispatch records complement provider claims and SQLite claim leases, while the application-level service remains replaceable by a webhook or remote queue adapter later.

# Alternatives Considered

- Provider webhooks reduce latency but require public endpoints and separate configuration for each work system.
- An external job queue improves distributed coordination but adds deployment and operational complexity before remote workers exist.
- In-memory intervals are simple but lose idempotency, attempt history, and recovery state on restart.

# Consequences

New work is observed at the configured polling interval rather than immediately. One process is the intended scheduler owner in v0.1. Persisted boundaries and deterministic keys make a later distributed lease implementation possible without changing workflow or provider contracts.

# Implementation Notes

The control plane starts configured scheduling after restart reconciliation. Manual CLI runs do not start background polling. Scheduler events use the shared event bus, and secrets or issue bodies are not copied into dispatch records.
