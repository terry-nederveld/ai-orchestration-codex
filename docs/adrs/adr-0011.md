# Context

The original approval manager waits on an in-memory Promise and times out pending approvals after a restart. This cannot support minutes-or-days suspension, multiple response surfaces, or exact checkpoint recovery.

# Decision

Use one persisted `WaitCondition` abstraction for human input, approval, time, external event, dependency, provider availability, and work-item events. A waiting node checkpoints before releasing active resources. Signals are idempotent and atomically select the first valid response. Later valid responses are retained only as supplemental context.

Typed human requests normalize responses into durable `HumanInput` events. Authorization is evaluated before a response may satisfy a condition. Resumption reloads the pinned snapshot and checkpoint; it does not depend on a live provider session.

# Rationale

A durable condition makes process lifetime irrelevant and provides one mechanism for otherwise similar suspension cases.

# Alternatives Considered

- Keep a process alive while waiting: rejected as fragile and expensive.
- Use provider conversations as checkpoints: rejected because sessions persist conversation, not authoritative filesystem or business state.
- Build a separate approval queue: rejected because it duplicates wait and event semantics.

# Consequences

The control plane must expose pending needs and signal submission. Recovery now distinguishes resumable waits from interrupted non-checkpointed work.

# Implementation Notes

Condition IDs and signal IDs are idempotency keys. Expiration is resolved by the scheduler and persisted like any other signal.
