# Context

The application needs a provider-rich orchestration core, a headless CLI, an HTTP control plane, extensive deterministic testing, and a web-based desktop UI. Provider SDKs and MCP have strong TypeScript support. The core must remain independent from the desktop shell.

# Decision

Use strict TypeScript on Node.js 22 or newer for the domain, application, infrastructure, control plane, and CLI. Use ECMAScript modules and expose contracts through explicit modules. The desktop shell may use another language only at its host boundary.

# Rationale

One language across provider integrations, workflow execution, the CLI, and UI-facing contracts reduces adapter friction. Node provides mature process, filesystem, HTTP, streaming, and provider SDK support. Node 22 is the minimum because it includes the built-in SQLite module without an opt-in flag.

# Alternatives Considered

- Rust for the entire platform would produce compact binaries and strong safety but would increase integration and UI delivery cost for the initial provider set.
- Go would simplify single-binary distribution but has weaker first-party coverage for several agent SDKs and UI integration.
- Python has broad AI SDK support but complicates a polished self-contained desktop distribution and shared frontend contracts.

# Consequences

The core is fast to extend and shares types with the UI. A Node runtime must be embedded in desktop distributions. CPU-intensive or untrusted work must run outside the event loop. The project must track Node's SQLite stability and maintain migration tests.

# Implementation Notes

Keep domain modules free of Node-specific imports. Infrastructure adapters own process, filesystem, network, and SQLite access. Target Node.js 22 and test on the current and active LTS lines.
