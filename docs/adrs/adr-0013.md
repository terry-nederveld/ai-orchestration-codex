# Context

The v0.1 desktop connects to one loopback runtime. Phase 2 requires simultaneous local and remote observation without suggesting that runtimes share credentials, storage, repositories, or orchestration state.

# Decision

The desktop is a federated viewer and control surface. It stores independent connection descriptors, fetches and streams each runtime independently, and tags every displayed record with its runtime ID. Groups are UI-only views. Tokens, errors, caches, actions, and event streams never cross connection boundaries.

Workflow design edits canonical YAML through an authenticated runtime API. Visual state is derived from parsed canonical text, and serialization round-trips semantically. Evaluate calls are explicitly read-only and return explanations rather than executing side effects.

# Rationale

Runtime authority enables clients to disconnect while work continues and prevents accidental cross-runtime actions or credential leakage.

# Alternatives Considered

- Replicate runtime databases into the desktop: rejected due to split-brain and secret exposure.
- Merge all connections behind one implicit workspace: rejected because it hides execution location and authority.
- Make visual graph state canonical: rejected because versionable text must remain portable and reviewable.

# Consequences

Every action must carry a runtime scope. Partial connection failure is normal and must not blank healthy runtimes.

# Implementation Notes

New activity is presented reverse-chronologically. The UI preserves a reader's historical scroll position and signals newer events.
