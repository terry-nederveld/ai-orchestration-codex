# Context

The product must discover providers, tools, workflow actions, hooks, and skills without editing the kernel. MCP servers provide tools and resources over a protocol but are not equivalent to trusted application extensions.

# Decision

Load application extensions from versioned manifests that declare entry points, contributions, compatibility, and permissions. Register contributions in narrow typed registries. Connect MCP servers through a dedicated client adapter and expose their tools only after capability and permission filtering. Load skills as focused, metadata-indexed documents on demand.

# Rationale

Manifests permit validation and discovery before executing extension code. Separate trust and lifecycle models prevent an MCP server from silently gaining application-extension authority. On-demand skills reduce context use.

# Alternatives Considered

- Scanning and importing arbitrary modules without manifests prevents preflight permission review.
- Treating every MCP server as a plugin conflates a remote tool protocol with in-process code.
- Injecting every skill into every prompt wastes context and weakens relevance.

# Consequences

Extension APIs need compatibility versioning. In-process extensions are trusted code and require clear warnings; future isolation can move the same registration protocol across a process boundary.

# Implementation Notes

Support global, user, project, and workflow scopes with deterministic precedence. MCP HTTP authorization follows the current OAuth guidance; stdio credentials are provided to the process without entering model messages.
