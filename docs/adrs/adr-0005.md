# Context

Direct inference APIs and existing coding-agent runtimes have different lifecycle, authentication, tool, persistence, and billing semantics. Providers expose unequal features.

# Decision

Define independent `ModelProvider` and `AgentProvider` ports. Every provider reports typed capabilities and availability. Routing selects providers by required capabilities and policy constraints rather than vendor-name branches. Authentication strategies and secrets are injected separately.

# Rationale

The distinction lets the native agent loop use direct APIs while workflows can delegate a complete coding turn to Codex, Claude Code, or Copilot. Capability negotiation makes unsupported combinations fail before execution.

# Alternatives Considered

- A single provider interface obscures who owns the loop and produces leaky optional methods.
- Vendor switches in the orchestrator are simple initially but make every new adapter a core change.

# Consequences

Routing and contract tests become first-class components. Provider metadata must represent partial support and multiple consumption models accurately. Adapter implementations remain somewhat different internally.

# Implementation Notes

Codex integration should use its supported SDK for automation and app-server only where its deeper authentication/event surface is required. Subscription authentication must use documented provider flows and never browser-cookie extraction.
